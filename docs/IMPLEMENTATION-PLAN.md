## 1. Authority, starting point and completion boundary

The confirmed MVP scope is all four connected flowchart sheets, including their branches, loops, exceptions and closure conditions. Use [PRD.md](PRD.md) for behavior and acceptance, and [TRD.md](TRD.md) for technical, security, transaction and release controls. Implement the screen/journey design in [APP-FLOW.md](APP-FLOW.md), the proposed constraints in [DATABASE-SCHEMA.md](DATABASE-SCHEMA.md), and the seven module responsibilities in [BACKEND-ARCHITECTURE.MD](BACKEND-ARCHITECTURE.MD). Use the [published glossary](PRD.md#22-domain-glossary) for terminology.

The original planning review also inspected local NOTE.md, CONTEXT.md, FLOWCHART-SOURCE-INVENTORY.md and FLOWCHART-COVERAGE.md. The original v2.0 DOCX remains historical source evidence when a diagram detail needs inspection. This GitHub-facing plan references the equivalent [source-node/branch coverage in TRD Appendix C](TRD.md#appendix-c-source-flowchart-coverage), rather than requiring ignored local supporting files. PRD sections 3/21 and TRD Appendix C supply the documented corrections to diagram shorthand. Existing requirements are referenced, not copied into a new requirements baseline.

The checkout contains documentation and no working React/Laravel application, migrations or verified prototype. Applicable root/ancestor and target-directory instructions were inspected; no applicable AGENTS.md or CLAUDE.md was found. This plan creates no new domain definitions and changes no existing requirements.

Stages are development checkpoints, not reduced releases. Complete MVP acceptance requires all four workflows, every branch, loop, exception and closure condition, all AC-01–AC-23 and ADD-AC-01–ADD-AC-12, and the applicable technical/MIG evidence. A package demonstration proves only that package. Test records can support an academic demonstration; they do not authorize live stock, money, hosted activation or a production-complete claim.

### Shared schema and frontend coordination

Expand schema profiles and mandatory relationship tuples into reviewed migrations package by package. Retain chapter-consistent and same-parent/line/variant composite FKs, exact source alternatives, unique source effects, append-only history, unit-precision enforcement and correct payment-account reference scope. Validate actual DDL on the intended pinned MySQL/InnoDB engine; XAMPP/MariaDB or SQLite is not acceptance evidence.

Reserve migration names/order before parallel branches create them. Shared registry/identity/operation tables land first; each domain adds its owned tables and typed relationships. Where future modules form cycles, record the planned nullable/deferred relationship and add the enforcing FK in the owning integration migration before the affected operation is enabled. Do not merge a falsely “done” posting with unenforced integrity. After a migration merges, use a new additive migration rather than editing applied history. Test clean install and upgrade from the current main checkpoint. Separate setup fixtures from accepted IPC/RM opening movements.

Use one generated/shared transport type definition per contract, plus domain UI types owned by the relevant developer. Keep handover/evidence components reusable without putting approval or financial authority in React. Contract/schema changes include consumer updates and compatibility evidence in the same PR or explicitly ordered dependent PRs.

## 4. Package rules and checkpoint order

Each package below includes **D** database/constraints, **B** backend operation, **F** frontend and **V** verification. Glenn is the primary UI implementer for every package; the listed workflow owner coordinates its backend, database, tests and integration. Leader primarily reviews Glenn's UI and is the default reviewer of Efren's output. A workflow owner listed with an F deliverable coordinates that UI with Glenn rather than transferring frontend ownership. A contract-only package produces reviewable agreements rather than code. Every listed dependency is needed for that package's integrated completion, not necessarily for beginning an isolated preview. Requirements are inclusive ranges in the existing PRD/TRD. S1–S4 identify original source sheets; F-xx/S-xx identify APP-FLOW journeys/screens. No new requirement IDs are introduced by the Pxx planning labels.

Common completion checks for every application package: relevant DDL passes intended-MySQL validation; actual API and typed frontend are connected; current chapter/duty/policy/version checks and field feedback work; required negative/branch/retry tests pass; records/history remain traceable; package source/AC evidence is recorded. Critical posting packages additionally demonstrate atomic rollback, duplicate/lost-response lookup and the relevant concurrency race. Required signature, stock or money gates use real implementations. One reviewed merge to main and a repeatable demonstration are required; screenshots or mocked happy paths alone do not close a package.

## 7. Three-developer branch, review and merge process

1. Keep `main` runnable and demonstrable. Start short package branches such as `plan-P09-po-approval`; split a package into small dependent PRs when necessary, each with a stated remaining integration gate. Do not leave three long-lived developer branches to combine at the deadline.
2. Before editing shared tables/contracts/types, reserve the change in the proposed registers and notify the affected developer. Reuse the agreed baseline. Each PR states package, requirement/source IDs, provider/consumer dependencies, schema/API compatibility, demonstration steps and actual checks. No ticket publication is required by this plan.
3. Require one nonauthor reviewer and green applicable CI. Leader is the default reviewer for Glenn's and Efren's PRs, including their UI and domain output. Leader-authored PRs require Glenn or Efren as a nonauthor reviewer. Cross-module stock/Finance/evidence/authority changes also receive the affected maintainer's integration review; authors cannot review their own changes. Shared migration/contract changes need Leader's coordination. Keep PRs small and make the review queue visible; any fallback to nonauthor peer review is an explicit team arrangement. These are technical reviews, separate from operational approvals.
4. Merge provider changes before consumers. Rebase/update against current main, rerun impacted checks, then merge. Apply migrations exactly once in integration, verify clean/upgrade paths, rebuild typed client and run the touched connected scenario. Avoid incompatible halfway contracts; combine a small provider/consumer change or retain explicit compatibility until both land.
5. At each active work session, identify current ready packages, changed interfaces and blockers. Integrate completed PRs frequently, with a short three-person connected walkthrough at every stage exit. Preserve linked record IDs and test logs so failures can be reproduced. Assign defects to module owners and hold the affected completion checkbox open.
6. Tag a reproducible checkpoint/release candidate with frontend/backend image/build IDs and schema version. Keep rollback/forward-recovery instructions matched to that schema. No force-push to shared main, history edits to applied migrations or direct fixes to posted records.
