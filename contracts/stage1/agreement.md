## Browser and authentication state

Use same-origin JSON requests with `credentials: 'same-origin'`, `Accept: application/json` and `Content-Type: application/json` for defined bodies. The cookie session is stored server-side in shared MySQL; there is no JWT, localStorage credential or client-selectable role. Unsafe requests require exact configured `Origin`, URL-decoded `XSRF-TOKEN` in `X-XSRF-TOKEN`, and the anonymous/continuation/full `ysp_session` cookie. The OpenAPI security requirement combines cookie and header with AND, not alternative authentication methods. Always check origin and CSRF, including sign-in and sign-out. Reinitialization synchronizes CSRF without changing identity. Use trusted proxy forwarding only from explicitly configured proxies; foreign origins are never credentialed CORS callers. CSRF initialization allows same-origin Fetch Metadata (or an exact same-origin Origin/Referer when Fetch Metadata is absent); deny `Sec-Fetch-Site: cross-site` even without an Origin header. A bare non-browser client is not a browser-origin approval.

Both cookies are host-only, `Path=/`, `SameSite=Lax`, `Secure`; `ysp_session` is `HttpOnly`, `XSRF-TOKEN` is readable for the header. Neither has a persistent lifetime attribute. Emit them as two separate Set-Cookie fields. Only deliberately isolated loopback HTTP may omit Secure; tunneled/non-loopback access requires HTTPS with correct public-origin/proxy configuration. Every auth response, including errors and 204, sends `Cache-Control: no-store`. No secrets appear in URLs, Referer, logs, tracing, audit payloads or browser persistent storage; service workers must not cache these responses. Only synthetic values are published here.

| State | Allowed auth operations | Prohibited capability |
| --- | --- | --- |
| Anonymous CSRF | initialize, password sign-in, sign-out | Session reads return 401; no enrollment, challenge, recovery metadata or business access |
| Enrollment continuation | session read, begin/confirm enrollment, sign-out, CSRF sync | Challenge/recovery use → continuation_mismatch; metadata/rotation → mfa_incomplete; all protected business reads/writes/subscriptions denied |
| Challenge continuation | session read, authenticator or recovery challenge, sign-out, CSRF sync | Enrollment → continuation_mismatch; metadata/rotation → mfa_incomplete; all protected business access denied |
| Password-only full, no enrolled factor | session read, voluntary first enrollment/confirmation, sign-out, CSRF sync | Recovery metadata/rotation → factor_not_enrolled; privileged actions requiring MFA remain denied if grants change |
| MFA-full, authenticator or recovery method | session read, recovery metadata, protected rotation, sign-out, CSRF sync | No automatic chapter access; no repeat first enrollment or challenge; rotation still needs fresh password and TOTP |

Enrollment continuation/challenge continuation are ten-minute absolute contexts from password acceptance and never renewed by reads or failed attempts. Full authentication has a two-hour inactivity expiry and twelve-hour absolute expiry from completed authentication. `expires_at` is the earlier effective deadline. Successful protected activity may renew inactivity only up to the absolute deadline. Rotation and secret-delivery replay do not reset the absolute start. These exact durations, one-year recovery expiry, five-minute delivery window and rate limits below are **proposed technical contract decisions for review**, not fabricated approved chapter settings or operational thresholds.

An enrolled officer challenges even if not currently required by duty. Approvers/administrators without a factor receive enrollment continuation. MFA-required status comes from current provider/operational authority; it is recomputed on every request. A newly required factor demotes a password-full session to the matching continuation with a new ten-minute deadline and invalidates existing private subscriptions. Demotion happens once per policy transition, not afresh on every read; it cannot prolong an existing continuation. Existing challenge/enrollment continuations keep their next step until completion or expiry even if duty requirements relax. No cookie marked full can bypass the server's current policy check. Disabled/revoked/expired sessions become 401 before any protected data or selector validation.

On password acceptance and MFA completion, invalidate the old ID and CSRF proof and issue new cookies. The old ID cannot regain access through an action-key replay. Serialize factor confirmation, recovery consumption, rotation, disabling/reset and session promotion so a simultaneous code use wins at most once. Use constant-work password failure for absent/disabled accounts and uniform factor failures. A matching code time-step is accepted once per account, even across browsers. Store enabled/pending TOTP seeds encrypted, recovery verifiers as one-way protected hashes and no plaintext proofs in ordinary session/audit records. Codes contain independent cryptographic randomness. Consumption/rotation/reset and history must commit together; failed proof or stale set changes neither factor nor recovery availability.

Logical revocation is authoritative at the mutation/access boundary, including cached outputs and queued deliveries. Sign-out revokes this browser and its pending enrollment/delivery receipts; it does not delete attribution or disable other sessions. Disabling invalidates all identity sessions and codes; controlled reset invalidates existing factor, sets and sessions and requires fresh password/enrollment. Exact administrative actors, verification approvals and command I/O are ticket 02's prerequisite, not a public API here. Losing a factor cannot be fixed by first-enrollment replacement. A recovery-authenticated officer can work only within current grants and must use controlled reset to replace a lost authenticator. Recovery codes cannot authorize recovery-code rotation in place of fresh TOTP.

## Errors, input and request ordering

Canonical request/response objects are closed and required keys are explicit in OpenAPI. Absent means no supplied value; null is allowed only where the schema includes null (current recovery set / expected set). Empty password, empty code, empty login, `null`, unknown fields and wrong JSON types are invalid. A nonempty password is verified exactly, without trimming. Recovery/TOTP codes are exact strings; numeric TOTP input loses leading zeroes and is rejected. No auth operation accepts query parameters or a body on its defined bodyless method. Malformed JSON, duplicate JSON keys/headers, query keys or invalid/missing action keys produce 400; media type violations on JSON-body operations produce 415; schema violations produce 422 with request-relative RFC 6901 field pointers. An unknown field pointer names that input key; a missing-field pointer names the required key. Error messages never echo supplied credentials or distinguish invalid/expired/used codes. Request IDs are opaque correlation IDs and confer no lookup access.

Enforce cheap trusted-IP throttling before expensive password/proof work. For unsafe calls, origin then CSRF precede account/proof/input details. Next validate current session/account and state, then media/syntax/schema, scoped key/fingerprint and action-specific fresh proof/state, then atomic transition. For an anonymous sign-in, check syntax/schema before credentials; for protected calls, deny missing/limited access before disclosing validity of a resource identifier. Proof failure is 403 `invalid_factor`, malformed proof shape is 422, expired continuation is 401, foreign/expired/unknown enrollment is uniformly 409 `enrollment_expired`. Non-JSON gateway errors are transport failures, never schema-valid committed results.

Apply a sliding 60-second trusted-IP budget of 60 requests across auth endpoints and a separate five-proof-attempt budget per keyed login identity for password sign-in, and per account for password/TOTP/recovery verification. Unknown logins get the same keyed bucket treatment. All proof attempts, including failures, consume the proof budget; retries do not bypass limits. A rejected throttle attempt consumes no action key or recovery code. Return 429 `throttled` with positive integer-seconds `Retry-After` (maximum remaining delay across applicable buckets). Tune only through a reviewed contract change; these are not officer-approved chapter policy values. Production capacity/rehearsal evidence is not supplied by these examples.

## Action keys and uncertain authentication results

All POSTs carry `X-Action-Key` UUID. Scope is the anonymous browser context and operation for sign-in, then immutable user + originating browser authentication lineage + operation for other actions. Bind the key to a keyed cryptographic fingerprint of exact validated request values (including enrollment/expected-set ID), never a plaintext password/code digest vulnerable to offline guessing. No public key-lookup API is provided by ticket 01. Current account, session lineage, authority and CSRF always precede replay. Maintain accepted key/fingerprint tombstones until the lineage expires; keep sign-in promotion tombstones through the resulting session lifetime. Failed validation/proof/state checks and pre-commit rollback do not consume the key or proof; rate-limit/audit records may still change. A different payload for an accepted key returns 409 `action_key_conflict` only to a currently authorized lineage.

| Operation | Same-key/same-payload retry and recovery |
| --- | --- |
| signInWithPassword, completeAuthenticatorChallenge, completeRecoveryChallenge | Accepted intent is consumed, not replayable to create/promote a second session. If new cookies arrived, inspect session and continue; repeated POST returns 409 action_already_used. If cookies were lost, old ID is invalid: initialize a fresh anonymous session and restart password sign-in using a fresh intent. A used recovery code stays used; use another code or controlled recovery. Never use action keys as authentication proofs. |
| beginAuthenticatorEnrollment | Return the same pending enrollment secret only to its still-current originating session and exact password-verified intent, while pending and unexpired. No second factor is created. Expired pending enrollment is removed and a new intent is required; no old secret replay. |
| confirmAuthenticatorEnrollment, rotateRecoveryCodes | Retain encrypted code-delivery result for five minutes, capped by session expiry, tied to resulting full session lineage + exact key/fingerprint + recovery-set ID. Same authorized browser with current password re-verification can repeat the identical request and receive the same set without consuming TOTP again or rotating again. Proof is checked freshly on first commit; a consumed TOTP is not re-consumed on delivery retry. Replay is denied if the set changed, a code was consumed, factor reset, session revoked or account disabled; return 409 secret_delivery_expired (401 if authentication ended). Erase encrypted delivery after the window; retained verifiers never reveal codes. Lost new cookies require fresh sign-in and then fresh password/TOTP rotation if the original delivery cannot be recovered. A recovery-only session cannot reveal a historical set. |
| signOutCurrentBrowser | Always safe to repeat with a current anonymous CSRF context. No secret/result retained. After cookie deletion, initialize new CSRF before repeating. |

For confirmation, replay admission checks a valid delivery receipt before requiring the now-consumed pending enrollment; for rotation it checks that receipt before testing the old expected-set ID or consumed TOTP. A current resulting full session is admitted only to evaluate its consumed-intent tombstone/delivery receipt; it cannot execute a new challenge or enroll an existing factor. The first commit and receipt are atomic. Otherwise legitimate lost-response recovery would be mistaken for an expired enrollment or stale version. Fresh rotation proof updates the displayed authentication_method/authenticated_at to authenticator completion while preserving the original absolute session deadline. Replays never roll back an already committed action. After an expired/unrecoverable code delivery, inspect safe metadata and explicitly rotate with new proof/key, rather than claiming an unseen set was not created. A 503/timeout is an uncertain result, not evidence that a code remains unused. These are narrowly authentication-specific exceptions to business result replay, not a substitute for ticket 08's durable posting lookup.

## Notification authorization boundary for ticket 09

Sign-in/MFA completion may enable later authorized subscription requests but never subscribes automatically or broadcasts a seed/code. Continuation has no business private-channel access. Sign-out, expiry, reset, disabling or MFA-policy demotion disconnect/invalidate the affected subscriptions; duty/chapter revocation requires fresh checks even if the session remains full. No delayed protected payload may be delivered using stale authority. Auth transitions issue no stock-change event. Ticket 09 will define the exact notification/channel authorization operations, events and audience; no WebSocket route is guessed here.

On 401, mfa_incomplete or authorization loss, Glenn clears protected rendered data/subscriptions immediately and keeps unfinished text only in memory, quarantined to its immutable user + original chapter. Reauthentication by the same person requires current authority and explicit conflict review before resubmission. A different identity must not see or reuse another person's retained form; discard/quarantine it without disclosure. Reconnect/refetch uses current permitted HTTP reads, never replays a mutation or treats notification loss as rollback. No numeric notification timing or three-laptop success is claimed.

## Contract validation

Use Python 3.13+ in an ignored workspace-local virtual environment. Pinned direct validation dependencies are in `validation-requirements.txt`; they are separate from runtime dependencies. `validate.py` is a contract-scoped invocation of the standards validator and JSON Schema validator, not a generator, global verifier or CI change. All canonical references are local JSON Pointers. It rejects dangling/nonlocal references, checks OpenAPI 3.1.1 structure, resolves every referenced schema, validates inline request/response/header examples and consumer cases against their exact operation/status, and checks example/operation coverage. Formats are asserted as well as schema structure. Deliberately invalid sample mode must exit nonzero because a recovery code is a number.

From this worktree root in PowerShell:

```powershell
python -m venv .runtime/contract-validation
.runtime/contract-validation/Scripts/python.exe -m pip install -r contracts/stage1/validation-requirements.txt

# Expected exit 1, invalid RecoveryChallenge payload; retain output as negative evidence:
.runtime/contract-validation/Scripts/python.exe contracts/stage1/validate.py --invalid-example
```
