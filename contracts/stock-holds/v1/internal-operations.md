# Hold operations and shared guards

Revision `1.0.0-review.1`. `inventory.record_stock_hold` and `inventory.clear_stock_hold` are normalized **internal** application operations. No HTTP route or source-free stock mutation is introduced. Inventory owns their outer transaction; Access and Documents participate on the same MySQL connection without independent commits. When a source workflow owns an outer operation, these participants join that operation. Efren alone implements actual physical posting; Glenn implements queries/reservations. All acceptance checks below remain future runtime obligations.

## Authority, source and evidence

Derive actor/current chapter/duty on the server using the identity, record and evidence contract, never from body flags. Recheck active user, chapter membership, effective duty/independence, policy/readiness, visible source record, exact material/hash, expected row/material versions and allowed transition inside commitment. `context.record` equals `finding.record` or `resolution.record`; context chapter, material version and source chapter agree. `hold_id` belongs to that chapter and the requested resolution actually targets that hold/source/identified cells. A source record kind alone confers no permission. Required approval/signature/evidence policy is loaded, not invented from fixture values. Missing configured authority or approval blocks; ordinary overrides cannot lift donor restrictions.

Documents resolves every supplied binding against the persisted ready evidence object and binding/material-pin tuple from the identity/evidence and IPC/RM contracts: same chapter/record/material/hash, intended purpose, exact immutable byte hash/storage version, actual required signer identity and accessible validated bytes. `hold_finding` binds to the finding; `hold_clearance` binds to the authorized resolution. Retain the original finding pins too. The server derives the required set so omission of a binding cannot reduce requirements. Stage uploads/external object checks before long locks; recheck readiness/identity/health under Documents consumption locks. Missing/unready/rejected/wrong-target evidence blocks. Hash integrity alone proves no authority.

## Ordered transaction protocol

Use `docs/DATABASE-SCHEMA.md` §10 and the IPC/RM acceptance contract's shared order, with ascending stable IDs inside each class:

| Order | Participation |
| --- | --- |
| 1 | Access user/membership/duty authority roots. |
| 2 | Chapter control/entitlement/readiness and policy effective-version guards, including absent-block fencing. |
| 3 | Chapter/action/key operation identity; finding/resolution and affected demand/source header rows with explicit versions. |
| 4 | Existing item-variant guards, then allocation-group/supply-source guards. **Every** hold, allocation, expiry, clearance, restriction and movement writer locks the same variant root exclusively, even for different purpose keys or absent hold rows. |
| 5 | Payment/funding/credit/protection roots for any affected paid/funded demand, before stock rows. Hold-only clearance does not debit or release money. |
| 6 | Lot/restriction/position/coverage/hold/reservation roots and projections, ordered consistently by class and ID; lock all positions currently touched by a reason's live coverage. |
| 7 | Documents bindings/readiness/material pins, required sequence fence if any, then immutable events/audit/result and durable tasks. |

Discover the complete dependency set first. If current locked state reveals another earlier-class dependency or position, rollback and restart with the complete set and unchanged attempt identity. Existing variant guards serialize an empty active-hold set; an unlocked `SELECT` for absent holds is no protection. Proposed isolation remains the schema's `READ COMMITTED`, to pin/test at runtime. Use locking current reads for every participating table, not a screen snapshot or an assumed implicit lock in a nested read. MySQL describes these semantics in [Locking Reads](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html). No `SKIP LOCKED` partial inventory snapshot is acceptable for commitment.

For each new identity, compare all supplied guard pins to the complete current dependency set, re-evaluate current time/restrictions/protection and the union, then use conditional expected-version updates and assert affected row counts. A stale pin returns scoped current state with no business effects; a refresh/corrected intentional attempt follows uncertainty resolution, never silent substitution of expected versions. No writer may rely on an eligibility-key lock alone because different purposes may cover the same lot cells.

## Record, clear and expire

1. **Record hold:** Resolve the finding's affected physical subset from persisted authorized evidence. Validate the internal coverage proposal is within current identified stock/lot/position, positive and quantum-aligned. If necessary split/refine cells with complete inherited memberships. Add this reason's membership and immutable finding/source/actor/evidence events; it may overlap an existing reservation. Do not reject a legitimate hold just because paid goods are reserved. Keep protected obligations and mark them blocked. Change no physical quantity or condition; reconcile and increment affected guards.
2. **Clear hold:** Load all of the identified reason's current live coverage through lineage and current assignments, not merely its original position. Recheck approved evidence-linked resolution and exact hold row version. Clear **only that reason in full**; partial clearance is outside this revision. Append clearance actor, reason, source/resolution versions, evidence, operation and history; remove only its active memberships. Recompute all remaining holds/reservations/restrictions. Clearing A succeeds even if B keeps the goods unavailable. A hold-only resolution changes neither recorded physical quantity nor condition and has `movement_ids:[]`.
3. **Expire reservation:** Only the currently unpaid/unprotected SO portion at its stored UTC deadline can expire. RF and paid/funded protection remain. Split a mixed-protection reservation into exact homogeneous cells/portions under payment/demand/variant guards before releasing eligible coverage. Append reservation history, drop only released ownership, update the intersection/guard/result and required notification intent. Holds stay. No receipt or increase in on-hand occurs.
4. **Condition treatment:** Clearing a hold on an actually quarantined cell can close that reason but cannot change its position/condition, accepted provenance or supply status. A later approved source-linked Inventory treatment moves the exact cells with its physical movement, appropriate approvals/evidence and protected-commitment reconciliation. Held/rejected inbound stock requires its authorized acceptance/source workflow; hold clearance alone never turns it into accepted usable goods. Later-found stock/corrections retain approved ADJ controls.

## Durable result, rollback and fingerprint

In one outer transaction append source progress and hold/reservation/coverage projections and immutable events, actor/evidence-linked audit, complete operation identity/fingerprint/result and required durable follow-up intent. `HoldChangeResult` reports original source, resolution (non-NULL for clearance), actor, reason, pins, hold/guard versions, affected live cells, no physical changes and audit/tasks. No post-commit task is allowed to re-clear or repost stock. Render/notify only after commitment; failed tasks remain visible for idempotent recovery.

Any participant/constraint/conditional-write/event/audit/result/task failure rolls back **all** provisional effects. Persisted earlier evidence/source and real physical facts are not undone. If retaining a terminal rejection, do so only after rollback in a no-business-effect transaction that rechecks authorization and the chapter/action/key uniqueness; never overwrite a concurrent success. `blocked` examples illustrate that optional durable rejection, whose `committed_at` is the rejection-result transaction time, not a stock posting time. A transient failure may instead have `operation:null` under the shared envelope.

Use the shared transport contract's exact fingerprint wrapper `{chapter_id,action_code,input_schema,input}` and RFC 8785 JCS/UTF-8/SHA-256. `input_schema` identifies the specific create/clear definition in `urn:ysp:stock-holds:v1`. `input` includes every command field, retaining context record and explicit row/material versions but excluding context chapter/action/key (chapter/action move to the wrapper). Preserve coverage/guard/evidence pins, reason and source/resolution hashes. Normalize range coordinates to six decimal places; sort coverage by numeric lot, position, start, end; reject duplicate or overlapping selection intervals. Sort position pins by numeric ID and evidence by numeric binding ID, rejecting duplicates. These arrays are sets; do not reorder a narrative string. Clear input has no coverage-selection array. No mutable latest-file, inferred balance or actor input enters the fingerprint.

Same chapter/action/key and payload replay is checked after current visibility/authority but **before** stale guards/cleared-state checks. Return the original durable references/versions/time with `replayed:true`, even if current stock has changed. A new key cannot re-clear a cleared hold: state and append-only terminal clearance uniqueness give `HOLD_ALREADY_CLEARED` without a second effect. Changed payload/key reuse rejects. Bounded deadlock retry repeats the **entire** transaction with unchanged identity/fingerprint and fresh checks, never a participant-only retry or second physical action.

Use the shared transport contract's chapter+action+key lookup or chapter-scoped known operation ID on lost response. No visible terminal result and unavailable lookup both remain uncertain; preserve original attempt/payload/key and local input. Never infer failed clearance/zero stock or mint a new attempt to bypass uncertainty. Wrong chapter, invisible target and revoked authority all return the same redacted forbidden envelope. Errors do not reveal other chapters' coverage/source IDs.

## Concurrency design proofs (expected)

The serial point is the conflicting variant guard plus current position/hold/reservation checks in the owning application operation, not the query token alone.

| Competing operations | Required observable serial outcomes |
| --- | --- |
| Clear A vs allocate while B still covers the goods | Either order leaves B active; allocation of B's cells blocks. Clearance never frees B's coverage. |
| Clear final hold vs two demands for those cells | Allocation before clear blocks; after clear exactly one demand can own each cell. The other blocks/stales. Unique live reservation ownership is a final defense. |
| Create hold vs allocation | Hold first: allocation sees active membership and blocks. Allocation first: hold attaches to that now-reserved coverage, keeps the commitment and blocks any subsequent use. Already allocated units do not become new free stock. |
| Create hold vs actual handover | Handover rechecks under the same roots. If hold wins, no held unit can post as handed over. If handover has committed first, a new finding cannot target already-consumed stockroom cells; physical uncertainty requires reconciliation, never fictional stock. |
| Two clearances of same reason / different reasons | Same reason has one terminal clearance; same-key replay returns it. Different reasons serialize and recompute remaining union without decrementing a shared total twice. |
| Split/expiry/restriction change vs hold/allocation | Every writer takes the same variant root; inherited links, current protection and current eligibility are rechecked. Stale geometry/tokens cannot evade another reason. |

`verification-cases.json` records concrete schedules and expected outcomes. These are design proofs only. Later consumers verify them at the **highest integrated owning application-operation boundary**, with real Access, Documents, Inventory/reservations/results, valid accepted-source stock and intended MySQL, including two connections and fault injection. Do not create a public test-only balance setter or test private ORM helpers as a substitute.
