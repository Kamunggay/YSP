# Opening acceptance operation and participants

Revision 1.0.0-review.1; expected contract, not executable business logic. Purchasing/Receiving (Leader) owns `purchasing.accept_opening_rm`. Inventory (Efren) owns the physical-posting participant. Documents owns record/evidence/result infrastructure. Access owns current authorization. Participants share the **same intended-MySQL connection and outer transaction**; none commits, opens an independent transaction, dispatches irreversible work or returns durable success before the owner commits. Glenn owns source/query screens.

## Inputs and read models

`AcceptOpeningInput` is a normalized internal boundary, not a public generic command. A future owning HTTP adapter supplies authorized chapter/action and `Idempotency-Key` using the shared transport contract; no route is finalized by this slice. Body inputs propose the RM material tuple, explicit expected RM row/material versions, IPC `SourcePin` with its row version/material/hash, and immutable `EvidencePin`s. The server loads the persisted `InspectedReceipt`, IPC `VersionedSource`, effective configuration and actual `EvidenceBinding`s. Inputs contain no actor, approval, eligibility flag, authoritative quantities, balances or client-selected Inventory destinations.

Every chapter equals the authorized chapter. Context record equals receipt record; expected material equals receipt material. Inspection target/state/material agree, and inspection.source equals input.source.target. Each RM line belongs to that RM; each IPC line belongs to that IPC; variants agree across both typed lines. Stable line IDs are unique within their material. Current source row/material/hash must match independently of RM concurrency. A partial progress update never manufactures new material. A material change requires a new immutable snapshot and affected approval/evidence; never replace a preserved expected version silently.

`InspectionMaterial` is canonical immutable RM content. Hash with the identity, record and evidence contract's exact UTF-8 JSON encoding, with keys in schema required-list order at each object: top-level `chapter_id,record,source,inspection_at,inspector,representatives,policy,lines`; line keys in `InspectionLine.required` order. Nested reused definitions use the identity, record and evidence contract's existing canonical order, record `id,kind`, quantities `value,quantity_scale`, source material `chapter_id,record,material_version,material_hash`. Attribution and policy use their schema property order. Normalize quantity/unit-valuation strings to six places; preserve six-place UTC instants; sort lines by numeric stable line ID and representatives by numeric user ID, no float conversion. Reject duplicate line/representative IDs and invalid Unicode. Policy/member changes are revalidated as current facts, not hidden by an old hash. Evidence is separately pinned to this hash; it is not included recursively in the material it signs. Actual count, inspection, entry, verification and posting times retain their separate meanings; commit/posting time is server-owned UTC, displayed in Asia/Manila.

## Baseline eligibility and quantities

Before commitment, validate current chapter setup/rollout/block/entitlement policy allowing the opening action, approved cutoff and suspended informal movements, complete signed count for the declared scope, at least two distinct counter user identities with one independent of the regular custodian, required genuine counter and Chapter Head/Finance signatures, authorized current source approval and valuation/restriction/item policy. Required ROP/target approval is a readiness input; it is not invented from fixture values. Authorized opening/setup before live activation does not start the trial or authorize issues/sales. Baseline commitment does not by itself activate live Gate 1.

Purchasing/Receiving checks source specifications, variant, actual quantities, packaging/quality/condition, inspector and required technical/requesting representatives. Empty representatives is admissible only when current requirements need none. In this first complete opening batch, every signed IPC line has one inspected RM line at the same source dimensions; conditions/locations are split into separate signed source lines. Expected equals counted; delivered + missing equals expected; delivered = accepted + rejected + held; recorded nonusable ≤ rejected + held. All arithmetic uses exact decimal strings/approved unit scale and cumulative source limits. No quantity may silently vanish or be accepted twice. Missing/uncounted/undocumented goods create no position. Genuine unresolved count discrepancies remain visible; reconcile/revise/reapprove affected source material when required before baseline acceptance, without inventing a blanket new policy or a second IPC after posting.

Only inspected accepted usable units enter accepted lots/usable stock. Rejected/held units stay unavailable; when their physical custody is documented, Inventory records a separate nonusable lot/position with documented quantity, **accepted quantity zero**, and a source-linked `rm_nonusable_intake` receipt movement. A nonusable receipt is not accepted supply progress. Unrecorded rejected/held portions retain discrepancy/custody follow-up, never become usable implicitly. The example records all two damaged units in nonusable custody. Restrictions remain attached; acceptance alone does not make restricted goods available for every use. Source-linked lot acceptance facts mirror initial accepted units once and are not an extra receipt.

One chapter opening comprises the complete committed source slice and fence, including its accepted/nonusable split and required cutover linkage. Do not post independent opening pieces and later add to the locked baseline. A separately approved carried-obligation/custody design is a P26 input, not implemented here. Later-found goods, recount differences and condition corrections use approved ADJ; they cannot reopen a posted IPC or create another opening RM.

## Lock and guard protocol

Use the shared schema §10 order with locking current reads. Intended InnoDB `READ COMMITTED` remains a proposal to pin/test at runtime. No reliance on gap locks for an absent baseline, stock position or active block. Acquire needed rows in ascending stable ID in each class. Resolve the complete dependency set before locks; if new dependencies appear, roll back and restart in order with the same identity/fingerprint.

| Order | Participant and conflicting writers |
| --- | --- |
| 1 | Access locks user/auth, membership/duty/alternate/MFA authority roots for fresh checks; disable/revoke/duty changes take conflicting locks. Cached context/attribution confers no authority. |
| 2 | Chapter control/readiness/entitlement and policy guards. Use an existing chapter singleton guard also when `chapter_openings` is absent; baseline contender takes exclusive guard. Setup, block, activation and policy writers follow the same order. |
| 3 | Chapter/action/key operation identity and fingerprint; then full sorted IPC/RM/CUTOVER records, current immutable versions, approval requirements/decisions, count/source limits and existing source-effect rows. Source edits/reapproval and other acceptance paths serialize here. |
| 4 | Inventory item variant guards, then any affected allocation/source guards. These exist even for zero stock; concurrent catalog/condition/restriction/eligibility writers participate. |
| 5 | Payment/claim roots if actually involved under another contract. **No payment/PO allocation is part of this opening slice.** Never acquire a later category then backtrack. |
| 6 | Inventory lot/restriction/location-custody/position/hold/reservation rows and projections. Create absent positions under unique dimensional keys and variant guard; on duplicate reread the locked row. Never use matching quantities as stock identity. |
| 7 | Documents evidence binding/readiness rows, required sequence fence, then effect/history/outbox rows. Validate exact ready objects, signatures and material pins **before** any stock effects. |

Documents checks current readiness and availability of exact pinned nonempty validated bytes before consuming evidence; an earlier upload/check is insufficient. Stage/upload/byte validation completes before this operation. Where object retrieval is external, preflight it outside long locks, then validate the current readiness/health identity inside commitment; a failure or detected missing bytes blocks acceptance. Storage deletion/archive/readiness transitions must conflict with consumption locks; independently lost storage is a recovery failure requiring reconciliation, not a guarantee that MySQL commits object storage. No mutable latest-file substitution. Ready hash integrity alone is not proof of signer identity. The required evidence set includes the source signed sheet, RM inspection and discrepancy evidence when applicable. Omitting a pin cannot lower required coverage; pins resolve to authorized record/line/material/binding purpose. The first slice does not impose an unrelated customer handover signature/batch rule on IPC.

## Owner sequence and atomic result

1. Prevalidate transport without changing business state; derive actual actor and complete dependency set. Begin the one outer transaction and acquire guards/locks in order. Recheck current Access authority, effective policy, chapter readiness and source/inspection relationships within commitment.
2. Resolve chapter/action/key under its unique key. Compare the shared transport contract's canonical fingerprint (also see below). An existing same-payload result is replayable only after current authorization to see the original source/result; return its original references/version/time. Check this replay before rejecting the now-locked opening fence or stale original versions. Changed payload reuse rejects without effects. An in-flight identity must wait/lookup; no terminal row proves no failure.
3. For a new identity, revalidate exact row/material/hash, approved source/counter/signature coverage, inspected quantities/restrictions/valuation and all current evidence; test absent chapter baseline under singleton guard. Register source action/batch uniqueness independently of request key. A new key cannot bypass posted source or opening uniqueness.
4. Purchasing/Receiving finalizes RM/source progress and discrepancies and the once-only opening/CUTOVER fence. Inventory consumes a **server-resolved** plan of the exact RM, IPC, typed lines and quantities described above. It alone writes source-linked posting, lots, nonusable/usable positions, positive movements, initial acceptance facts and projections. Documents validates/pins evidence; no registry or report can post stock. All writes remain provisional in this transaction.
5. Append immutable actor/source/material/evidence-linked audit, durable operation identity/fingerprint and complete `AcceptedOpeningResult`, plus required durable tasks (e.g. projection/report refresh and damage follow-up). A refresh task reads committed facts and must not repost stock. The saved result has the returned operation/record/baseline/posting/lot/position/movement/discrepancy/audit/task references. Successful progress advances RM 4→5 and IPC 8→9 in the fixture, retaining material 1 and approvals; exception stays open while the baseline locks.
6. Commit once. Only then return success and lease/dispatch follow-up. External rendering/notification and physical handling are outside the transaction. Task retries reuse stable business identity and cannot duplicate posting. A later task failure leaves the committed receipt intact and exposes durable failed/retry status, not a fabricated receipt rollback.

Operation fingerprint follows the shared transport contract `api-v1.json#x-fingerprint-contract`: build `{chapter_id,action_code,input_schema,input}`, apply **RFC 8785 JCS** (recursive lexicographic member ordering), encode UTF-8 without BOM and hash SHA-256. `input_schema` is `urn:ysp:ipc-rm-acceptance:v1#/$defs/AcceptOpeningInput`. `input` retains every semantic command field: the context's `record,expected_row_version,expected_material_version`, plus `receipt,source,evidence`. Move context chapter/action into the wrapper; exclude only context idempotency key and the shared transport exclusions. `evidence` explicitly has set semantics: sort by numeric binding ID and reject duplicate binding IDs. Retain optional line nulls; all exact IDs/versions/material hashes/object versions/purposes participate. Quantities are pinned through immutable material hashes, so no untrusted balance/authority enters the input. **The fixed-order material snapshot encoding above is a separate algorithm; do not use it for operation fingerprints.** [fingerprint-vector.json](fingerprint-vector.json) supplies the literal expected wrapper, canonical bytes and digest for `accept-input`. Keep identical payload/pins for lookup/retry; a corrected material/expected-version submission is a new intentional attempt after resolving any uncertainty.

## Rollback, retry and uncertainty

Any failure after any provisional write—including Inventory, baseline, audit, result or durable task write—rolls back **all** acceptance effects on the shared connection. No committed RM progress, source quantity, lot, position, movement, baseline, audit success or follow-up survives alone. Earlier persisted drafts, signed source, completed evidence uploads/bindings and actual physical counts remain historical facts; rollback does not undo real goods or files. No participant catches failure and returns success. Domain blocking errors use typed shared envelopes and preserve local input; unauthorized/wrong-chapter/unknown invisible records use the same redacted forbidden response. More precise parent/variant/evidence details require visibility of all referenced records.

Bounded deadlock/unique-conflict retry reruns the whole transaction with unchanged chapter/action/key/fingerprint and fresh checks, never a participant-only retry or another physical count/handover. Duplicate winners resolve to the saved authorized result or the source/baseline blocker. A transaction failure has no committed operation success; if a terminal rejection is retained it must use a separate no-business-effect rejection transaction after rollback, with current authorization and the same unique identity, and must not overwrite a concurrent success. The authored failure fixtures use `operation:null` and do not claim durable rejection persistence.

A lost response may hide a committed opening. Use the shared transport contract scoped `OperationLookup` by authorized chapter + action/key, or known operation ID. No terminal result visible means `pending_or_not_visible`; lookup failure means `unavailable`. Both preserve original draft/attempt/payload/key and uncertainty. Do not create a new key, repeat physical activity or report zero stock from missing lookup. Once visible, return the stored result with `replayed:true`; current changed stock does not rewrite the original result. Revoked access redacts the result rather than authorizing replay.

P06 verifies all of these rules through the real owning operation, intended MySQL, actual Access/Documents/Inventory participants and valid source stock. This contract supplies no fake authorizer, stock API or executed transaction simulation.
